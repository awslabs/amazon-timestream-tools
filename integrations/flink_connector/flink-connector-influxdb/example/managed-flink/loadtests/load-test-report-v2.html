Instance types: 3 x db.influx.16xlarge (InfluxDB 3 Enterprise), writing to ingest node yeet-16xl-1's endpoint; 3 x db.influx.large (InfluxDB 3 Enterprise: 2 ingest/query nodes, 1 compactor); db.influx.medium (InfluxDB 3 Core). Revisions: 0ec9e2d. Generated 2026-10-19 18:44 UTC.

Rates and p50 are means over each run's steady-state minutes; p95, p99, and CPU are the highest minute. Node CPU % is each InfluxDB node's mean CPU; a node near 0 received no writes.

Bottom line: the connector writes about 165K rows/s per KPU and scales close to linearly: 1.23M rows/s with 8 KPUs at p99 802 ms. The InfluxDB instance sets the limit, up to 1.68M rows/s (180 MB/s) on one 16xlarge ingest node.

Takeaways

  • The connector is not the bottleneck. Each writer is CPU-bound at about 165K rows/s and throughput adds up close to linearly until the InfluxDB instance stops keeping up.
  • Size by the destination. One 16xlarge ingest node takes about 11 writers; past that, KPUs only add latency (p99 7.2 s at 16 writers). To go further, write to more ingest nodes.
  • Small instances need fewer requests in flight. At the default of 8, Core medium retried 43,088 rows and restarted; at 2 it ran clean at 126K rows/s.
  • The Enterprise cluster endpoint pins each writer to one ingest node: 2 and 4 writers on Enterprise large all landed on one node and stopped near 180K rows/s.
  • High cardinality costs throughput, not stability, and the soak showed no leaks.

Recommendations

Writers ≈ ingest node ceiling ÷ 150K rows/s × ingest nodes, rounded up. For 100K–10M series, plan for 10–20% fewer rows per writer.

Test setup

loadtest,run=16xl-p8-sustained-1,host=host-42 f0=13.02,f1=92.21,f2=71.40,f3=50.59 1760548627000042000
  • Rows of 101–107 bytes: measurement loadtest, tags run and host, four float fields, nanosecond timestamps; 1,000 series unless noted. Sent in 10,000-line batches (about 1 MB), gzip on the wire.
  • Generated inside Managed Flink by the example's datagen pipeline at an unlimited rate, checkpointing on, one sink subtask (writer) per KPU. KPU counts include the orchestration KPU Managed Flink adds.
  • Each run: warm-up, then 5 steady-state minutes (15 for 8 writers on the 16xlarge).
  • Destinations: Core db.influx.medium; Enterprise 3 × db.influx.large via the cluster endpoint; Enterprise 3 × db.influx.16xlarge via one ingest node's endpoint.

Caveats

  • One row shape. Wider rows or more fields mean fewer rows/s per writer.
  • Each configuration ran once. The 16xlarge node once stalled for about 28 minutes and recovered; a later 15-minute run at the same settings did not stall.
  • The 16xlarge cluster's second ingest node was idle, so total cluster capacity was not measured.
  • The soak ran below capacity, so a leak that only appears under heavy load could be missed. Real HTTP 429 responses were not covered; no cluster returned one.
